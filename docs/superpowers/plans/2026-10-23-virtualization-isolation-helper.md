### W4 local SDK process-observation evidence — G0 disposition (2026-10-24)

**Version and review scope.** `xcrun --sdk macosx --show-sdk-version` returned macOS SDK 27.0; `sw_vers -productVersion` returned host macOS 26.6.2. `manifest.json:5` sets Obsidian `minAppVersion` 1.12.7; this is separate from the native helper deployment target, which remains unresolved (this Plan's Task 0, line 72; Spec line 93). A read-only `find -L` enumerated all public `.h` header filenames under the two frameworks' `Headers` directories: Virtualization 140, Hypervisor 22. A keyword scan covered that filename enumeration; declaration review was limited to the exact cited ranges below. This does not mean every header's contents were read or every Apple API was exhausted.

- **VM lifecycle:** state/start/stop/requestStop and delegate stop/error callbacks describe VM lifecycle, not guest workload PID, lineage, or exit; `requestStopWithError:` asks the guest to turn itself off (`Virtualization.framework/Headers/VZVirtualMachine.h:24–56,58–75,124–128,214–221,234–254,335–342`; `Virtualization.framework/Headers/VZVirtualMachineDelegate.h:16–34`).
- **Console and serial:** console port open/close callbacks identify the device/port only, without PID, lineage, or process result, and a console device conflicts with VA2 (`Virtualization.framework/Headers/VZVirtioConsoleDevice.h:17–25,28–44`). `VZFileSerialPortAttachment` is guest-output-to-host-file; `VZFileHandleSerialPortAttachment` is bidirectional. Both remain guest-controlled and neither attributes bytes to a guest process (`Virtualization.framework/Headers/VZFileSerialPortAttachment.h:12–20,25–39`; `Virtualization.framework/Headers/VZFileHandleSerialPortAttachment.h:12–19,24–43`).
- **Storage:** disk-image attachment exposes RAW image/read-only/configuration, not a guest-PID-attributed write-event callback (`Virtualization.framework/Headers/VZDiskImageStorageDeviceAttachment.h:55–79,81–111`; related declarations: `Virtualization.framework/Headers/VZStorageDeviceConfiguration.h:30–35`; `Virtualization.framework/Headers/VZVirtioBlockDeviceConfiguration.h:12–30`). A shared filesystem device exposes a host resource to the guest and is forbidden by VA2.
- **Custom Virtio and guest memory:** SDK 27.0 Custom Virtio (available on macOS 27.0) and guest memory APIs are device/memory interfaces, not documented process/filesystem hooks; adding Custom Virtio conflicts with VA2. Guest queue data is mutable by the guest (`Virtualization.framework/Headers/VZCustomVirtioDevice.h:19–42,80–99`; `Virtualization.framework/Headers/VZCustomVirtioDeviceConfiguration.h:19–44,46–99`; `Virtualization.framework/Headers/VZCustomVirtioDeviceDelegate.h:15–47,58–93`; `Virtualization.framework/Headers/VZCustomVirtioDeviceDelegateProvider.h:14–20`; `Virtualization.framework/Headers/VZGuestMemoryMapping.h:12–24,31–50`; `Virtualization.framework/Headers/VZVirtioQueueElement.h:12–29`). Graphics display declarations were also reviewed (`Virtualization.framework/Headers/VZGraphicsDisplay.h:68–92`).
- **Hypervisor:** declarations expose VM memory and vCPU controls for a VM associated with the current host process/thread, not guest process/filesystem events or a documented observer for an existing `VZVirtualMachine` (`Hypervisor.framework/Headers/Hypervisor.h:10–34`; `Hypervisor.framework/Headers/hv_vm.h:19–72`; `Hypervisor.framework/Headers/hv_vcpu.h:19–39,383–406`; `Hypervisor.framework/Headers/hv_vm_allocate.h:27–60`).

**Bounded conclusion:** within the enumerated local SDK 27.0 public header set and targeted declaration review above, no documented host API was found that provides independently trustworthy guest PID, direct parent/child identity, workload completion, or guest filesystem-write attribution for an existing VZ VM while preserving the fully untrusted guest and VA2. This does not prove no API exists elsewhere, does not claim runtime behavior was tested, and is not architectural impossibility.

**Disposition: VA1/VA5 and Task 0 G0 remain unresolved; G0 stays NO-GO.** This evidence does not change acceptance criteria or establish architectural impossibility. Reopen G0 only if a supported, independently trustworthy host API for an existing VZ VM is evidenced that can bind guest process identity, direct parent-child relation, process completion, and guest-write attribution while preserving VA2; otherwise keep G0 blocked.
